# Private backend protocol for the coding agent

LabLedger runs inside the current Codex or Claude Code session. You conduct the
conversation, create JSON requests, invoke the bundled helper, and interpret its
responses. The user never needs to prepare payload files or run backend commands.
Do not install a separate LabLedger distribution or look for a global executable.

## Invoke the bundled helper

Resolve the plugin root from this document's location: its parent is `resources/`
and the next parent is the plugin root. Use the absolute path to
`scripts/backend.py` under that root. Select an available Python 3.11+ interpreter.
The helper prepares pinned dependencies in `$XDG_CACHE_HOME/labledger/runtimes/`
(or `~/.cache/labledger/runtimes/`) on first use. Initial setup needs package-index
access; later requests reuse the environment. The plugin and research project's
dependency configuration are never edited for runtime setup. Host permissions apply.

Create the request yourself in an OS temporary directory, then invoke it through
the host's command tool using this shape, replacing paths with actual absolute paths:

```sh
python3 -I -B "/absolute/plugin/scripts/backend.py" < "/absolute/temp/request.json"
```

Quote paths and serialize JSON with a JSON encoder or the host's file-writing tool.
Do not interpolate user text into shell code. A request has this shape:

```json
{
  "operation": "init",
  "root": "/absolute/research/repository",
  "arguments": {"dry_run": true},
  "payload": {"name": "Discussed project name", "charter": "Agreed charter Markdown"}
}
```

`root` is always required and absolute; it is the actual ledger root, not an
arbitrary subdirectory or the plugin folder. Discover `.labledger/config.toml` in
ancestors for an existing ledger. For first init, agree the repository destination.
`arguments` defaults to `{}`. Omit `payload` for operations that do not accept one.
The helper reads one request per process and writes one JSON response to stdout:
`{"ok":true,"code":0,"result":...}` or `{"ok":false,"code":N,"error":"..."}`.

Codes: 2 invalid request/schema, 3 conflict, 4 missing prerequisite, 5 integration
or storage failure. Fix payload errors yourself from schema and evidence; ask only
when an actual user decision or missing fact is needed. Never hide an unsuccessful
operation. A failed run returns code 1 (130 for cancellation) **and a result** with
the durable run record; inspect it and preserve the attempt. The actual child exit
code stays in that record. Do not retry experiments merely because a request failed.
Runtime setup failures affect only the cache; diagnose them in this session.

In native Plan Mode, inspect bundled schema/files and discuss without writing to
the project. Keep proposed JSON in conversation or use stdin where permitted;
defer persistence to execution. An existing runtime supports read-only operations
without writing project files. Do not bypass the host's restrictions to prepare it.

## Operations

Arguments below use JSON values: IDs/paths/text are strings, revisions are positive
integers, switches are booleans, and `argv`/`capture` are arrays of strings. Unknown
arguments are rejected. Updates use `expected_revision` from the latest read;
resolve conflicts from actual changes rather than overwriting another revision.
Identity, timestamps, and revision fields are generated by the backend.

| Operation | Arguments | Payload |
| --- | --- | --- |
| `version` | None | None |
| `schema` | Optional `kind` | None; inspect authoritative `$defs` in the result |
| `init` | Optional `dry_run` (false) | Optional object; first setup requires `name`, `charter`; optional `research_dir`, `artifacts_dir` |
| `task.new`, `decision.new`, `experiment.new` | None | Required record input |
| `finding.add`, `claim.add`, `probe.add`, `exposure.add`, `review.add` | None | Required record input |
| `<kind>.get` | `id`; optional `revision`, `include_restricted` (false) | None; kinds above plus `run` |
| `<kind>.update` | `id`, `expected_revision` | Required shallow patch; kinds above except `run` |
| `task.attach-plan` | `id`, `expected_revision`; optional `execution` (false) | Approved plan content and evidence, after leaving Plan Mode |
| `handoff` | `task`; `expected_revision` to generate; optional `check` (false) | Brief object to generate; omit for `check: true` |
| `run.start` | `experiment`, `argv`; optional `capture` ([]), `parent`, `retry_reason`, `cwd`, `metadata` (object) | None |
| `run.import` | Optional `source_name` | Required external run object or manifest; missing metadata stays unknown |
| `run.annotate` | `id`, `expected_revision` | Analysis/outcome/status payload |
| `run.reconcile` | `id`, `expected_revision`, `reason`; optional `confirm_stopped` (false) | None |
| `artifact.add` | `run`, `expected_revision` | Artifact metadata |
| `artifact.redact` | `run`, `expected_revision`, `path`, `output` | `reason`, `replacements` rules |
| `artifact.tombstone` | `run`, `expected_revision`, `path`, `reason` | None |
| `policy.get` | None | None |
| `policy.update` | `expected_revision` | Full `config`, `charter`, `approval_evidence` |
| `recall` | `query`; optional `task`, `limit` (10), `include_restricted` (false) | None |
| `status` | Optional `task`, `include_restricted` (false) | None |
| `resume` | `task`; optional `include_restricted` (false) | None |
| `report` | `task`; optional `output`, `include_restricted` (false) | None |
| `doctor` | Optional `repair`, `capabilities`, `include_restricted` (all false) | None |
| `cache.rebuild` | None | None |

Use `schema` with a record kind to inspect fields; init uses kind `init_input`.
The bundled `resources/schema.json` is also readable without runtime setup.
Read only the relevant definition. References use returned IDs and exact revisions:
`{"type":"decision","id":"actual-returned-ID","revision":1}`.
Record inputs omit generated identity and revision fields. Arrays and nested
objects in a patch replace the entire previous value.

## Content and workflow boundaries

Approval evidence is an object with `summary` and `source` describing actual user
confirmation. An existing explicit instruction can authorize bounded work. Do not
invent approval, message IDs, run outcomes, or planning evidence. Continue technical
steps already within the agreed scope without asking the user to operate the helper.

Handoff payload has `brief` sections `problem`, `scope`, `evidence`, `options`,
`direction`, `constraints`, `acceptance_criteria`, `open_questions` (Markdown strings)
and optional typed `references`. After generation, return the actual filled prompt
and fresh-session steps; do not begin implementation in the brainstorming session.

An execution-time plan payload has `content`, `brief_revision`, `decision_refs`,
`approval_evidence`, and `planning_evidence`. Persist it with `execution: true`, then
update task status to implementing before code changes. Discuss material departures.

Use `run.start` with real argv, never hidden shell interpolation. Only explicit
`capture` paths are snapshotted. Do not put secrets in request files or records.
Signal the helper process to cancel a running experiment; it cancels the process
group and preserves the attempt. Resume and doctor never relaunch runs.
Restricted data needs an explicitly requested evaluation analysis; never enable
`include_restricted` to improve development suggestions. Hooks only remind and never
prepare dependencies, approve, mutate records, or execute experiments.
